# 로드맵

앞으로 만들고 싶은 기능들을 정리한 문서. `README.md`는 "지금 있는 것"을 설명하고, 이 문서는 "앞으로 할 것"을 정리한다.

각 항목은 `상태` 로 진행도를 표시한다:
- **논의중** — 방향을 아직 정하는 중
- **확정** — 방향은 정해졌고 구현 순서만 남음
- **완료** — 다 만들어서 앱에 들어감

---

## 큰 그림

처음엔 하고 싶은 걸 9개로 나열했는데, 뜯어보니 **대부분이 하나의 기반 작업에 걸려 있었다.**

지금 앱은 운동 종목도 음식도 **그냥 문자열**이다 (`WorkoutExercise.exerciseName`, `MealEntry.menuText`). 그런데:

- 시간형 운동을 넣으려면 → 종목마다 "횟수형/시간형" 태그가 있어야 하고
- 목록에서 골라 넣으려면 → 종목에 고유 ID가 있어야 하고
- 남의 루틴에서 원하는 것만 가져오려면 → 같은 종목인지 판별할 ID가 있어야 하고
- AI가 기록을 이해하려면 → 역시 ID 기반 데이터가 있어야 한다

그래서 **카탈로그 계층(종목 DB · 음식 DB)이 나머지 거의 전부의 전제조건**이다. 이걸 먼저 만들고 나머지를 그 위에 얹는다.

### 의존 관계

```
0. 기반 정비 (마이그레이션 · 시드 버전 체계)
   └─ 1. 카탈로그 계층 ──┬─ 2. 운동 목적 설정 ─┐
                         ├─ 3. JSON 공유/백업 ──┤
                         │     └ 사용자 추가분 내보내기 = 시드 승격 재료
                         └──────────────────────┴─ 5. AI 챗
      6. 성능 — 1·5번에 딸려오는 작업

4. 폰-PC 동기화 (드롭박스 · CMP) ← 맨 마지막. 아래 참고
```

**드롭박스 동기화는 후순위로 미룬다.** 기술적으로는 0단계 뒤 언제든 가능하지만, 시작하려면 사용자가 드롭박스 개발자 콘솔에서 앱을 등록해야 하고, 무엇보다 **앱 자체가 쓸 만해지는 것(1·2·5번)이 먼저**다. 기기 간 데이터 이동은 그때까지 3번의 JSON 백업 파일을 손으로 옮기는 걸로 충분하다.

## 0. 기반 정비

**상태: 확정** · 다른 무엇보다 먼저

### 0-1. 파괴적 마이그레이션 제거 — **완료**

`fallbackToDestructiveMigration()` 때문에 **스키마를 바꿀 때마다 로컬 데이터가 초기화되던 것**을 없앴다. 앞으로 할 일이 전부 스키마 변경이라 그대로 뒀으면 작업할 때마다 데이터를 잃었다.

- `exportSchema = true` + ksp `room.schemaLocation` → `app/schemas/`에 버전별 스키마 JSON을 남긴다. **4.json이 이후 모든 마이그레이션의 기준선**이다
- `MIGRATIONS` 배열을 두고 버전을 올릴 때 여기에 추가하게 했다
- `MigrationTest` 3개가 "버전만 올리고 마이그레이션을 빠뜨리는" 사고를 잡는다. 실제로 버전을 5로 올려보고 `A migration from 4 to 5 was required but not found`로 실패하는 것을 확인했다

사용법은 `README.md`의 "DB 스키마를 바꿀 때" 참고.

### ~~0-2. Room WAL 끄기~~ — 취소됨

WAL을 끄려던 이유가 "동기화가 DB 파일을 복사할 때 `-wal`/`-shm`으로 쪼개져 깨지는 걸 막기 위함"이었는데, **동기화 단위를 DB 파일에서 JSON으로 바꾸면서** 파일을 만질 일이 없어졌다. WAL은 켜둔 채 성능 이점을 유지한다. → `SYNC-DESIGN.md`

### 0-3. 시드 버전 체계 — **완료**

`ensureRoutinesSeeded()` 류가 "테이블이 비어 있으면 넣기"라 **최초 1회만** 동작했다. 앱을 업데이트해서 시드를 늘려도 기존 사용자에겐 영영 반영되지 않는 구조였다.

- `app_meta` 테이블에 `seedVersion`을 기록하고, 내장 `SeedData.VERSION`이 더 높을 때만 밀린 단계를 돌린다 (`Repository.applySeeds()`)
- 데이터 주입을 **Room 마이그레이션에 넣지 않는다.** 버전마다 누적돼서 금방 감당이 안 된다. 앱 시작 시 별도 단계로 처리한다
- **`seedVersion`은 DB에 둔다** — 동기화 메타데이터를 DataStore에 두는 것과 반대다. "이 기록 뭉치에 어느 시드까지 반영됐나"라서 **데이터를 따라다녀야** 하고, 그래서 JSON 스냅샷에도 실린다. 옛 백업을 불러오면 버전이 낮아져 밀린 시드가 다시 채워진다
- 앞으로 카탈로그 시드는 `source = SEED`인 행만 slug 기준으로 upsert한다. 사용자가 직접 추가한 것(`source = USER`)은 안 건드린다

**지금 시드(루틴·식단표·목표)는 재적용하지 않는다.** 사용자가 고치는 콘텐츠라 다시 깔면 이름을 바꾸거나 종목을 뺀 걸 덮어쓴다. 그래서 1단계는 "첫 설치에만"으로 감쌌고, 실제로 버전을 올려서 재적용할 대상은 **카탈로그가 생긴 뒤**에 붙는다.

이 작업으로 **첫 실제 마이그레이션(4→5)** 이 생겨서 0-1의 machinery를 진짜로 검증했다.

## 1. 카탈로그 계층 (종목 DB + 음식 DB)

**상태: 완료**

기존 항목 중 "시간 vs 횟수", "종목을 목록에서 선택", "음식 DB"가 전부 여기로 합쳐졌다.

**진행 상황**
- [x] `exercise` 테이블 (slug · 부위 · 기구 · `trackingType` · `source`)
- [x] 추적 방식 5종 + `workout_set`에 `durationSec` / `distanceM`
- [x] 종목 카탈로그 시드 50개 — 앞의 27개는 기존 루틴의 종목명을 그대로 써서 **이름 완전일치로 100% 연결**됨
- [x] 종목 검색·선택 다이얼로그(부위 필터, 직접 추가)
  - 숨기기가 있었으나 **폐기**했다(DB 9). 되돌리는 화면이 없어서 사용자에겐 삭제로 보였고,
    50개짜리 목록에서 굳이 감출 이유가 없었다. 숨겨져 있던 종목은 마이그레이션에서 다시 나온다
- [x] 세트 입력이 추적 방식에 따라 바뀜 (플랭크 → 시간(초) 칸)
- [x] **루틴이 세트를 그대로 담는다**(DB 10, `routine_set`) — 예전엔 기본 무게·횟수 한 쌍뿐이라
  세트 수도, 워밍업처럼 세트마다 다른 무게도 못 담고 불러올 때 세 세트로 펴졌다
- [x] 스냅샷·xlsx 반영 — 시간형이 "0kg 0회"로 나가지 않는다
- [x] **음식 카탈로그** — 60여 개를 10개 분류로. 종목의 패턴(slug + source + 시드 단계)을 그대로 재사용했다. `hidden`은 음식에만 남아 있다(항목이 많아 감출 이유가 있고, 시드 음식은 지우면 되살아난다)

**음식만 다른 점**: `food_item`은 카탈로그가 생기기 전부터 "쓰면서 쌓이는" 용도로 이미 사용자 데이터가 들어 있었다. 그래서 마이그레이션에서 기존 행에 slug를 채운 **뒤에야** 유니크 인덱스를 걸 수 있었고, 시드는 이름이 겹치면 사용자 것을 그대로 둔다(직접 적은 영양정보가 더 정확할 수 있다).

### 규모 — 중간 시드 + 자동 축적 + 나중에 승격

- **종목**: 부위/기구/추적방식 태그를 붙여 **50개로 시작**(기존 루틴의 27개 + 흔한 23개). 처음엔 150~250개를 잡았다가 줄였다 — 쓰면서 부족한 게 드러나면 시드 버전을 올려 추가하면 되고, 그 경로가 이미 만들어져 있다
- **음식**: 자주 먹는 것 위주로 **60여 개** 시드(밥·곡물/육류/생선/유제품/두부·콩/채소/과일/견과/간편식/음료). 나머지는 지금처럼 쓰면서 자동으로 쌓임
- **승격 경로**: 사용자가 직접 등록한 항목들이 쌓이면, 그걸 뽑아내서 다음 앱 버전의 시드에 합친다. 즉 **시드는 쓸수록 자라는 구조**다

수만 건짜리 공공 식품 DB를 통째로 넣는 안은 버렸다 — 데이터 정제가 앱 개발보다 큰 작업이 되고, 대부분 평생 안 쓸 항목이라 검색 품질만 떨어진다.

### 설계 요점

**stable slug를 정체성으로 쓴다.** 카탈로그 항목마다 `bench-press-barbell` 같은 문자열 키를 두고, Room의 auto ID는 로컬 전용으로만 쓴다. 시드 갱신을 slug 기준 upsert로 하면 **앱을 업데이트해도 기존 기록의 참조가 깨지지 않는다.** (0-3의 전제)

**`source` 구분**: `SEED`(내장) / `USER`(직접 추가). 시드 갱신은 SEED 행만 건드린다. 사용자가 SEED 항목을 고치면 USER 행으로 복사해 분기시켜서, 나중 갱신이 사용자 수정을 덮어쓰지 않게 한다.

**기록은 ID를 참조하되 이름도 같이 남긴다.** `exerciseId: Long?`을 추가하되 기존 `exerciseName` 문자열도 유지한다. 이유가 둘 있다 — 카탈로그 항목의 이름이 바뀌거나 지워져도 과거 기록은 그대로여야 하고, 엑셀 내보내기가 어차피 이름 기준으로 동작한다. ID를 nullable로 두면 카탈로그에 없는 걸 자유 입력하는 지금 방식도 계속 쓸 수 있다.

**시간형 운동은 nullable 컬럼으로 넓힌다.** `WorkoutSet`에 `durationSec: Int?`, `distanceM: Double?`를 추가하고, 카탈로그 종목에 `trackingType`(무게×횟수 / 시간 / 거리+시간 / 맨몸횟수)을 붙인다. 종목을 고르는 순간 알맞은 입력 칸이 뜬다.

범용 `metricType` + value 컬럼 방식은 버렸다. 추적 방식이 몇 종류 안 되는데, 범용으로 가면 볼륨 계산 같은 곳마다 값을 해석하는 코드가 붙는다. SQLite는 NULL 컬럼 비용이 거의 없어서 이쪽이 단순하고 빠르다.

## 2. 운동 목적 설정 — **완료**

목표 화면에서 **목적(벌크업/유지/컷팅) + 활동량(적음/보통/많음)** 을 고르면, 최근 체중으로 권장 칼로리·매크로를 계산해 보여준다.

**자동으로 목표를 바꾸지는 않는다.** 체중을 잴 때마다 목표가 조용히 달라지면 사용자가 자기 목표를 신뢰할 수 없다. 권장값을 보여주고 "권장값으로 채우기"를 눌러야 칸에 들어가며, 숫자를 직접 고치는 기존 방식도 그대로다.

계산은 `TargetCalculator`에 따로 빼서 화면 없이 테스트한다:
- 유지 칼로리 = 체중 × 활동계수(29/33/37) — 정밀한 TDEE 공식은 키·나이·성별이 필요한데 이 앱은 안 받는다. 어차피 실제 체중 변화를 보며 조정하는 게 정석이라 시작점으로 충분하다
- 목적 보정: 벌크업 +12%, 컷팅 −18%
- 단백질 = 체중 × 1.8g (컷팅은 2.2g — 칼로리를 줄일 때 근손실을 막으려면 오히려 더 챙겨야 한다)
- 지방 = 총칼로리 25%, 탄수 = 남은 칼로리, 당 = 총칼로리 10%(WHO 권고 상한)

`goal`/`activityLevel`은 DB에 남는다 — **5번(AI 챗)이 "지금 벌크업 중"이라는 맥락을 여기서 읽는다.**

- [x] 선택적 병합 — 파일을 열면 **전체 덮어쓰기 / 골라서 가져오기** 중에 고른다

**골라서 가져오기의 설계 요점**
- 고를 수 있는 건 **재사용 가능한 것**(루틴 · 식단표 · 남이 직접 만든 종목)뿐이다. 일별 기록은 뺐다 — 남의 하루 기록을 내 기록에 섞는 건 의미가 없고, 같은 날짜를 어떻게 합칠지는 레코드 단위 동기화 문제라 별개다
- **루틴이 쓰는 종목이 자동으로 따라온다.** 루틴은 종목을 slug로 참조하므로, 남의 종목이 내게 없으면 같이 들여와야 이름만 남고 추적 방식이 날아가지 않는다. 딸려오는 종목은 내 시드가 아니므로 `USER`로 들어간다
- **이름이 겹치면 덮어쓰지 않고 " (2)"를 붙인다.** 어느 쪽이 맞는지는 사용자만 아니까 둘 다 남기고 고르게 한다
- 되돌림점을 안 남긴다 — 아무것도 지우지 않으므로 마음에 안 들면 들어온 루틴을 지우면 그만이다

**엑셀 가져오기를 안 만드는 이유**: 엑셀 파서는 셀 위치가 조금만 어긋나도 깨지고, 항목 ID나 스키마 버전을 담을 데가 없다. "남의 파일에서 원하는 루틴만 골라 내 걸로 가져오기"는 결국 병합 작업인데, 병합에 필요한 정보가 엑셀에는 없다. JSON이면 slug로 안전하게 대조된다.

### 딸려오는 것 — 시드 승격

사용자가 직접 추가한 카탈로그 항목(`source = USER`)만 JSON으로 뽑아내는 기능이 여기 거의 공짜로 얹힌다. 그게 **1번에서 말한 "다음 시드의 재료"** 다.

## 4. 폰-PC 동기화

**상태: 설계 확정 · 착수는 후순위(맨 마지막)** · 상세 설계는 **[`SYNC-DESIGN.md`](SYNC-DESIGN.md)**

> 설계는 끝났지만 **구현은 다른 걸 다 한 뒤에** 한다. 앱 자체가 쓸 만해지는 게 먼저고, 그때까지 기기 간 이동은 3번의 JSON 백업 파일을 손으로 옮기면 된다. 설계를 미리 해둔 덕에 3번의 JSON 포맷이 그대로 동기화 payload가 되므로, 나중에 얹을 때 버릴 코드가 없다.

- **Dropbox API를 앱에 직접 연동** — 앱 전용 폴더. 로그인 한 번이면 그 다음은 자동. Google Drive보다 Dropbox를 먼저 (앱 등록이 더 간단함)
- **동기화 단위는 DB 파일이 아니라 gzip JSON 스냅샷** ← 설계 중 뒤집힌 결정
  - DB 파일을 주고받으면 **두 기기의 앱 버전이 항상 같아야** 한다. 한쪽만 업데이트하면 Room이 다운그레이드 마이그레이션을 지원하지 않아 깨진다. 그걸 잊는 게 정상이라 시간문제일 뿐
  - 그리고 3번에서 JSON 직렬화를 어차피 만든다. DB 파일 동기화는 **전송 메커니즘을 두 벌** 만드는 셈
- **동기화 시점**: 실시간 아님. **앱 열 때** 받고 **앱 내릴 때** 올림
- **충돌은 사전 감지** — Dropbox `rev`로 `WriteMode.update()` 하면, 그 사이 다른 기기가 올렸을 때 덮어쓰는 대신 거부한다. 백업이 *사고 후 복구*라면 이건 *사고 자체를 막는* 장치
- **업로드는 WorkManager로** — `onPause`의 저장 플러시가 지금도 결과를 안 기다리는데, 여기에 네트워크 작업을 얹으면 프로세스가 먼저 죽어서 날아간다
- **레코드 단위 자동 병합은 안 함** — `replaceDay()`가 자동저장마다 행 ID를 파괴해서 지금 구조로는 불가능. 이유와 선행 조건은 설계 문서 5장
- **PC용 앱은 Compose Multiplatform**으로 — 안드로이드 Compose 코드를 최대한 재사용
  - 확인 결과(2026): Room이 2.7.0+부터 **데스크탑(JVM)을 공식 지원**하고, 지금 쓰는 버전(2.8.4)이 이미 해당됨. 즉 `data/` 폴더(Entities/Dao/Repository)를 거의 그대로 재사용 가능하고, 플랫폼별로 다르게 짜야 하는 건 "DB 파일 위치를 찾는 방법"뿐. Compose Multiplatform 데스크탑 타겟 자체도 정식 프로덕션 레디로 확인됨

**남은 실행 순서**: Dropbox 개발자 앱 등록(사용자가 콘솔에서 직접) → 인증 + 업/다운로드 → 동기화 상태 기계 + 충돌 UI → CMP 데스크탑

앞단(JSON 직렬화·백업 UI·마이그레이션 정비)은 이미 끝났다. **그 덕에 드롭박스 없이도 수동 백업/복원으로 기기 간 이동이 된다.**

**버린 대안들**:
- 자체 서버(Firebase/Supabase) — 여전히 클라우드 계정/인프라가 생겨서 "서버 없는 개인 앱"이라는 장점이 사라짐
- 웹앱 하나로 통일 + 안드로이드는 웹뷰 껍데기 — 이미 만든 Compose UI를 전부 버려야 하고, 오프라인 우선이라는 앱의 정체성도 흔들리고, 엑셀 내보내기·파일 공유 같은 OS 기능 접근이 오히려 번거로워짐

### CMP 대비 — 지금 같이 해두면 싸다

`data/` 재사용이 확인된 만큼, 남은 걸림돌은 **도메인 로직이 400줄짜리 `MainViewModel`과 화면에 섞여 있다는 점**이다. 1번 작업을 하면서 순수 Kotlin `domain/` 패키지(안드로이드 import 0)로 같이 빼두는 게 나중에 뜯는 것보다 훨씬 싸다.

단 **지금 gradle 멀티모듈로 쪼갤 필요는 없다.** 패키지 분리 + "여기엔 android import 금지"라는 규칙만으로 충분하고, 실제 CMP에 착수할 때 모듈로 승격하면 된다.

## 5. AI 챗 (식단 추천 포함)

**상태: 확정**

"Claude Code를 앱에 심는다"는 건 불가능하다 — 컴퓨터에서 돌아가는 CLI 도구라 폰에 넣을 수 있는 게 아니다. 대신 **앱 안에 대화형 챗 화면을 만들고 각 API를 붙인다.**

### 형태 — 멀티 프로바이더 + BYOK

- **Claude / OpenAI / Gemini 중 골라서** 쓸 수 있게. 세 API 모두 messages 배열 + SSE 스트리밍 구조라 인터페이스 하나로 추상화된다
- **각 사용자가 자기 API 키를 설정 화면에 넣는다** (BYOK). 앱에 키를 박아두면 추출되므로 불가능하고, 개인/소규모 앱에는 이 방식이 맞다
- 호출할 때마다 **각자의 계정에서 소액 과금**된다

### 설계 요점

**API 키는 `EncryptedSharedPreferences`에 저장한다** (Android Keystore 기반). Room 평문 저장은 안 된다.

**AI가 앱 데이터를 봐야 의미가 있다.** 안 그러면 그냥 ChatGPT 앱을 쓰는 것과 같아서 앱 안에 있을 이유가 없다.

#### 컨텍스트는 세 겹으로 나눈다 (토큰 최소화)

데이터를 통째로 넣지 않고, **데이터의 지도**를 넣는다.

**1) 정적 — 제약·규칙** (repo에 md로 두고 버전 관리)

안 변하는 것들. 단위(kg/cm/kcal), 날짜 형식, 그리고 안 알려주면 AI가 확실히 틀리는 도메인 규칙:
- 매크로가 `null`이면 *모름*, `0`이면 *진짜 0* — 둘은 다르다
- 체지방률이 비어 있으면 체중·체지방량에서 계산된 값이다
- 끼니 이름은 고정 슬롯이 아니라 사용자가 자유롭게 붙인다

**2) 동적 — 매니페스트** (대화 시작 시 앱이 조립)

무슨 데이터가 얼마나 있는지의 목차. 데이터 자체가 아니다.

```
기록 기간: 2026-01-03 ~ 2026-09-02 (243일 중 187일 기록됨, 56일 공백)
종목: 34개 사용 중
  벤치프레스 41세션 (2026-01-08 ~ 2026-08-30)
  스쿼트 38세션 / 데드리프트 29세션 ...
  ※ 세트 상세는 이 대화에 미포함 — 필요하면 사용자에게 기간 첨부를 요청할 것
신체기록: 18건, 최근 2026-08-28
식단: 최근 30일 평균 2,480kcal · 단백질 158g (목표 2,600 / 165)
```

**있다는 사실과 지금 못 읽는다는 사실을 항상 같이 적는다.** "41세션"만 적으면 내용이 있다는 뉘앙스라 모델이 채워넣게 된다. 경계를 같이 주면 "모른다"에서 한 걸음 더 나아가 *"기간을 첨부해 주시면 볼 수 있다"* 고 안내하게 된다.

**3) 요약 통계** — 자주 물을 법한 것의 답을 미리. 주요 종목 최근 최고중량 추이, 체중 30일 추세, 오늘 기록 전체.

셋 다 합쳐 500~1,000 토큰 수준. 이것만으로 현실적인 질문의 상당수가 **조회 없이** 답해진다.

> **함정**: 매니페스트의 스키마 설명을 손으로 쓰면 안 된다. md에 적은 필드가 실제 스키마와 어긋나면 AI가 없는 필드를 근거로 추론하는데, 조용히 틀리는 종류라 발견이 늦다. **스키마 부분은 코드에서 생성**하고, 손으로 쓰는 건 코드로 만들 수 없는 도메인 규칙(1번)만.

#### 환각 방지 — 모르면 모른다고 답하게

**이 앱에서 가장 중요한 품질 기준이다.** 없는 숫자를 지어내면 기록 앱으로서의 신뢰가 통째로 무너진다. 프롬프트에 "지어내지 마"라고 쓰는 것만으로는 부족하고, **구조적으로 지어낼 여지를 없애는 쪽**이 훨씬 확실하다.

**가) 값마다 출처를 붙인다.** 이 앱은 `MacroEstimator`가 메뉴 이름으로 만든 어림값과 사용자가 직접 입력한 값이 섞여 있다. 구분 없이 넘기면 AI가 **추정치를 사실로 세탁한다.**

```json
{"kcal": 520, "source": "estimated"}   // MacroEstimator가 만든 어림값
{"kcal": 480, "source": "entered"}     // 사용자가 입력/확정한 값
{"kcal": null}                          // 모름
```

이러면 "오늘 몇 칼로리 먹었어?"에 *"확정된 2끼는 980kcal, 나머지 3끼는 추정치라 합치면 대략 2,400kcal 정도"* 라고 답할 수 있다. 뭉뚱그려 "2,400kcal 먹었네요"와는 질이 다르다.

**나) 빈 곳을 숫자로 명시한다.** "243일 중 187일 기록됨, 56일 공백". 이걸 안 주면 평균을 낼 때 빠진 날을 모르고 계산한다.

**다) "기록 없음"이 정당한 답임을 명시한다.** 정적 규칙(1번)에 `null` = 모름은 이미 있지만, 그것만으로는 성실하게 답하려다 메운다. *"데이터가 없으면 없다고 답하는 것이 옳은 답변"* 이라고 명시적으로 적는다.

**라) UI에 "이 대화에 포함된 데이터" 패널을 둔다.** 접을 수 있는 형태로, 이번 대화에 실제로 주입된 내용을 그대로 보여준다. 사용자가 AI가 뭘 보고 말하는지 직접 대조할 수 있다.

> 답변에서 숫자를 뽑아 주입 데이터와 자동 대조하는 검증도 검토했으나 보류. 평균·증감처럼 **정당하게 계산된 숫자가 오탐으로 잡혀서** 실용성이 없다. 위의 (라)가 더 싸고 효과적이다.

#### 그래도 "가져오는 경로"는 하나 필요하다

**있다는 걸 아는 것과 읽을 수 있는 것은 다르다.** 매니페스트만 있으면 "지난 3개월 벤치 추이 어때?"에 AI가 *"41세션이 있는 건 아는데 내용을 못 본다"* 고 답하거나, 더 나쁘게는 **숫자를 지어낸다.** 아무것도 모르는 것보다 위험하다.

경로는 세 가지가 있고, **두 개는 tool use가 아니다**:

- **결정적 사전 조회** — 보내기 전에 앱이 사용자 메시지에서 날짜·종목명을 뽑아 해당 구간만 붙여서 한 번에 보냄. 루프 없음, 프로바이더 무관, 3사 전부 즉시 동작. 다단계 질문엔 약함
- **사용자가 명시적으로 첨부** — "이 기간 기록 붙이기" 버튼. 가장 단순하고 예측 가능
- **tool use** — 모델이 필요할 때 스스로 조회. 가장 강력하지만 비용이 있다(아래)

**매니페스트 + 앞의 둘이면 tool use 없이 꽤 멀리 간다.** 그래서 tool use는 "결국 가야 할 곳"이 아니라 **"부족하면 그때 가는 곳"** 으로 둔다.

#### 조회 함수 계층을 먼저 만든다 (모든 경로가 공유함)

`domain/`에 **이름 붙은 조회 함수**들을 JSON 반환으로 정의한다:

```
getMealsByDateRange(from, to)              -> JSON
getRecentBodyRecords(n)                    -> JSON
getWorkoutHistory(exerciseSlug, from, to)  -> JSON
searchFoods(query)                         -> JSON
```

- **1단계 — 컨텍스트 주입**: 대화 시작 시 이 함수들을 앱이 직접 호출해 결과를 시스템 프롬프트에 넣는다. 루프 없음, 프로바이더 무관, 코드 경로 하나.
- **2단계 — tool use**: 같은 함수들을 tool 정의로 노출한다. **함수 본문은 안 바뀌고**, 프로바이더별 프로토콜 어댑터만 새로 짠다.

즉 1단계 작업이 2단계에 그대로 재사용되므로 버려지는 코드가 없다.

#### tool use를 2단계로 미루는 이유

비용이 데이터 모양이 아니라 **프로토콜과 루프**에 있기 때문이다. 데이터를 JSON으로 깔끔히 정리해도 이 둘은 안 없어진다.

- **프로토콜이 셋 다 다르다** — Claude는 `tool_use` 블록 + `tool_use_id`로 매칭, OpenAI는 `tool_calls` + `role: "tool"` 메시지(인자가 JSON *문자열*이라 파싱이 깨질 수 있음), Gemini는 `functionCall`/`functionResponse` part + **id 없이 이름으로 매칭**. 개념만 같고 세부가 전부 어긋난다
- **요청-응답이 아니라 루프다** — 호출 → 실행 → 결과 반환 → 또 호출... N회. 스트리밍 위에 얹힌 상태 기계라 루프 도중의 취소·타임아웃·에러를 다 다뤄야 한다

#### 언제 2단계로 넘어가는가

매니페스트 + 사전 조회로 안 되는 게 쌓이면 그때 간다. 구체적으로 **다단계 질문**이 걸린다 — "벤치랑 스쿼트 추이 비교하고, 정체된 시기에 체중이 어땠는지도 봐줘" 같은 건 무엇을 가져올지가 앞선 조회 결과에 달려 있어서 사전 조회로는 못 맞춘다.

넘어갈 때는 **Claude 어댑터 하나만 먼저** 붙여 루프를 검증한 뒤 나머지 둘을 붙인다. 프로토콜 3개를 동시에 디버깅하는 상황을 피하기 위함.

그리고 이때도 매니페스트는 그대로 쓴다 — 모델이 이미 뭐가 있는지 알고 시작하므로 **도구 호출 횟수가 줄어든다.** 1단계 작업이 2단계에서도 손해가 아니다.

**쓰기는 넣지 않는다.** AI가 기록을 직접 고치는 대신, "이 추천을 내 식단에 넣기" 버튼으로 사용자가 명시적으로 승인하게 한다.

**대화 저장**: `ChatSession` / `ChatMessage` 엔티티 신설. 히스토리를 전부 메모리에 올리지 않게 주의(6번).

## 6. 성능 (메모리/CPU, 논블로킹)

**상태: 논의중** — 1·5번에 딸려오는 작업

"이미 코루틴을 쓰니 충족"으로 정리했었는데, **그건 스레딩 문제만 해결한 것**이다. 실제 부담은 데이터 양과 네트워크 쪽에 있다.

- **전 기간 기록을 통째로 메모리에 올리고 있다.** `observeAllMeals()` / `observeAllWorkouts()`가 StateFlow로 전체를 들고 있어서, 기록이 몇 년 쌓이면 히스토리 화면이 전 기간을 상주시킨다 → 날짜 범위 쿼리 또는 페이징으로
- **AI 챗(5번)이 진짜 논블로킹 작업이다.** 스트리밍 응답은 취소·타임아웃·부분 응답 처리가 필요하다. "코루틴이라 논블로킹"만으로는 해결되지 않는다. 채팅 히스토리도 전체 로드하면 안 된다
- **카탈로그 검색(1번)** — 중간 규모(수백 개)로 정해서 당장은 단순 쿼리로 충분하다. 다만 시드 승격이 반복돼서 수천 건을 넘어가면 Room FTS4 + 검색어 디바운스로 전환해야 한다

지금 당장 할 일은 없고, 1번과 5번을 만들면서 같이 처리한다.
