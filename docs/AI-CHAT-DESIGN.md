# AI 챗 설계

`ROADMAP.md` 5번이 "무엇을 할지"라면 이 문서는 **"어떻게"** 를 정한다.

목표: **내 기록을 아는 코치와 대화한다.** 서버 없이, 각자 자기 API 키로.

| 항목 | 결정 |
|---|---|

| 스키마 | DB 12 (`chat_session` · `chat_message` · `ai_memory` · `ai_context_cache`) |

## 1. 왜 이 기능이 앱 안에 있어야 하나

**AI가 내 기록을 봐야 의미가 있다.** 안 그러면 ChatGPT 앱을 따로 쓰는 것과 같고, 그러면
이 화면이 존재할 이유가 없다.

그래서 이 문서의 절반은 "무엇을 어떻게 넣어줄 것인가"다. 나머지 절반은 "**넣지 않은 것을
지어내지 않게** 하는 방법"이다. 기록 앱에서 숫자를 지어내면 앱 전체의 신뢰가 무너진다.

---

## 2. 알고 있어야 하는 전제 — 모델은 기억하지 못한다

어느 프로바이더를 쓰든 채팅 API는 **무상태**다. 요청 사이에 남는 것이 없고, 가중치는 호출로 바뀌지
않는다. 그래서 "지난번에 무릎 아프다고 했잖아"가 성립하려면 **우리가 그 문장을 저장했다가
이번 요청에 다시 넣어야** 한다.

- 대화가 이어지는 것처럼 보이는 것 = 매 턴 이전 대화를 통째로 재전송하기 때문
- 개인화 = 우리가 저장한 사실을 프롬프트에 끼워 넣기 때문
- 파인튜닝은 답이 아니다 — BYOK 구조에선 사용자가 자기 모델을 학습시킬 방법이 없고,
  오늘 먹은 밥을 반영하려고 재학습할 수도 없다

**따라서 "기억"은 모델의 기능이 아니라 이 앱의 기능이다.** 이 문서의 §6이 그 설계다.

## 3. 프로바이더 붙이는 방법

### 3.1 어댑터를 셋 만들지 않는다

같은 문제를 이미 푼 오픈소스 클라이언트들(§15)을 보니 공통점이 하나 있었다.
**대부분 프로바이더별 어댑터를 만들지 않고 "OpenAI 호환 엔드포인트" 하나로 처리한다.**
Android 클라이언트인 Open Chat은 어댑터 하나로 OpenAI · Anthropic · Groq · OpenRouter ·
Mistral · Ollama · LM Studio · Together를 지원한다. 대부분의 프로바이더가 OpenAI의 요청
형식을 그대로 받아주기 때문이다.

그래서 이렇게 간다:

1. **OpenAI 호환 어댑터 하나** — OpenRouter · OpenAI · 로컬 모델까지 이걸로 커버
2. **Claude 네이티브 어댑터** — 프롬프트 캐시 등 이 앱에 실익이 있는 기능이 있어서
   (호환 엔드포인트로 되는지는 구현할 때 확인한다)
3. Gemini는 필요해지면 그때

### 3.2 기본 프로바이더를 정하지 않는다

**앱이 "이 회사를 쓰세요"라고 정하지 않는다.** 사용자가 이미 가진 키를 꽂으면 되는 형태다.
설정에서 저장하는 건 **연결 프로필**이고, 필요한 건 셋뿐이다.

```
이름       "내 OpenRouter"        (목록에서 알아보기 위한 것)
Base URL   https://openrouter.ai/api/v1
API 키     sk-or-...              (EncryptedSharedPreferences)
모델 ID    anthropic/claude-sonnet-5
```

- **프리셋은 입력 편의일 뿐이다.** OpenAI / OpenRouter / Anthropic / Gemini / Ollama를
  누르면 Base URL이 채워지고, 그대로 직접 쳐 넣어도 된다. 사내 게이트웨이든 로컬
  Ollama든 OpenAI 형식이면 붙는다
- **모델 목록을 앱에 박아두지 않는다.** 가능하면 `/models`로 받아와 고르게 하고, 안 되면
  직접 입력. 모델은 계속 새로 나오는데 앱 업데이트를 기다리게 할 이유가 없다
- **프로필을 여러 개 저장**하고 대화 중에 바꾼다. 요약·정리는 싼 모델, 상담은 좋은 모델

첫 실행에서 아무것도 미리 고르지 않는다. 프리셋 목록만 보여주고 사용자가 고른다.

### 3.3 대신 모델 능력 편차를 다뤄야 한다

자유도의 대가다. 아무 모델이나 꽂을 수 있으면 **도구 호출을 못 하는 모델**, **컨텍스트가
8K뿐인 모델**, **기억 추출을 엉망으로 하는 작은 로컬 모델**도 들어온다. Open WebUI 문서도
"작은 로컬 모델은 기억을 일관되게 저장·검색하지 못한다"고 못 박아 두고 있다.

프로필마다 **능력 플래그**를 두고 기능을 켜고 끈다.

| 플래그 | 없으면 |
|---|---|
| 도구 호출 | 조회·쓰기 기능을 UI에서 끄고 "이 모델은 조회를 지원하지 않습니다" 표시 |
| 컨텍스트 크기 | 예산을 그 크기에 맞춰 줄이고, 안 들어가면 저장하기 전에 경고 |
| 프롬프트 캐시 | 그냥 안 켠다 (비용만 조금 더 듦) |

#### 언제 알아내나 — 연결할 때 한 번 검사한다

**연결을 저장하는 순간 프로브를 돌린다.** 실사용에서 실패할 때까지 기다리지 않는다 —
사용자가 "6월 벤치 보여줘"라고 물었는데 그제서야 안 된다고 하면, 답도 못 받고 이유도
모른다. 처음에 알면 그 모델로 뭘 할 수 있는지 알고 시작한다. 프로브는 아주 짧은 호출
한두 번이라 비용이 1원도 안 된다.

검사 항목과 방법:

| 항목 | 방법 |
|---|---|
| 인증 · URL | 아주 짧은 요청 하나 |
| 스트리밍 | 같은 요청을 스트리밍으로 |
| **도구 호출** | 더미 `ping` 도구를 정의하고 **강제 호출**(`tool_choice`로 지정)로 시도 |
| 컨텍스트 크기 | `/models` 응답에 있으면 가져오고, 없으면 보수적 기본값 + 수동 입력 |

도구 호출을 "불러줘"라고 **부탁하면 안 된다.** 지원하는 모델도 안 부를 수 있어 미지원으로
오판한다. 강제 지정이 거부되면 그 자체가 미지원 신호다.

결과는 체크리스트로 보여준다. 안 되는 게 있으면 **그 기능을 꺼두고 무엇이 꺼졌는지** 적는다.

```
✅ 연결됨        anthropic/claude-sonnet-5
✅ 스트리밍
❌ 도구 호출     → 조회·기록 기능이 꺼집니다
   컨텍스트 200K
```

**Base URL이나 모델 ID가 바뀌면 플래그를 버리고 다시 검사한다.** 같은 프로바이더라도
모델마다 능력이 다르다.

#### 그래도 실사용 실패는 대비한다

프로브가 통과했는데 실제로 실패할 수 있다(프로바이더가 정책을 바꿨거나, 프로브가 오판).
그때는 조용히 죽지 말고 **자동으로 플래그를 끄고 알린 뒤 요약만으로 답한다.** 공짜
안전망이라 프로브와 같이 가져간다. 설정에는 **재검사 버튼**과 수동 덮어쓰기 스위치를 둔다.

**OpenRouter를 쓰면 키 하나로 거의 모든 모델을 쓸 수 있다**(3사에 각각 가입할 필요 없음).
대신 요청이 중개자를 한 번 더 지나므로 개인 건강정보가 한 곳 더 통과한다 — 설정 화면에서
이 차이를 알리고 고르게 한다.

### 3.4 왜 공식 SDK를 안 쓰나

SDK를 넣으면 APK가 커지고, 각자 다른 모델/스레딩/에러 타입을 앱 안에서 다시 통일해야 한다.
어차피 요청 구조가 같아서(HTTPS POST + messages 배열 + SSE 스트리밍) 직접 붙이는 비용이
크지 않다.

```kotlin
/** 연결 프로필 하나. 사용자가 설정에서 만든다(§3.2). */
data class AiConnection(
    val name: String,
    val baseUrl: String,
    val modelId: String,
    val capabilities: Capabilities        // 도구 호출 · 컨텍스트 크기 · 캐시 지원 (§3.3)
    // API 키는 여기 없다 — EncryptedSharedPreferences에서 따로 읽는다
)

interface AiProvider {                    // 지금은 OpenAiCompatible / Anthropic 둘뿐
    fun stream(conn: AiConnection, request: AiRequest): Flow<AiChunk>
    suspend fun listModels(conn: AiConnection): List<String>?   // 안 되면 null → 직접 입력
    suspend fun probe(conn: AiConnection): Capabilities         // 저장할 때 한 번
}
```

`AiRequest`는 프로바이더 중립이다(시스템 텍스트, 메시지 목록, 도구 정의, 상한).
각 구현체가 자기 JSON 모양으로 바꾼다. **프로바이더별 특수 기능은 최적화로만 쓴다** —
프롬프트 캐시는 켤 수 있으면 켜고 없으면 안 켠다. 기억과 대화 이력의 진실은 항상 우리
DB에 있어서, 연결을 바꿔도 아무것도 잃지 않는다.

> 구현 시 각 API의 정확한 요청/응답 모양은 그때 공식 문서로 확인한다. 기억으로 쓰면
> 필드 이름이 조용히 틀린다.

## 4. 데이터 모델 (DB 12)

기존 테이블은 건드리지 않는다. 네 개를 더한다.

```
chat_session      id · title · providerId · modelId · createdAt · updatedAt
chat_message      id · sessionId(FK) · role(USER/ASSISTANT/TOOL) · text
                     · toolName? · toolPayload? · tokensIn? · tokensOut? · createdAt
ai_memory         id · text · kind(FACT/OBSERVATION) · source(USER_SAID/AI_EXTRACTED)
                     · observedOn?(관찰한 날짜) · createdAt · updatedAt
ai_context_cache  key · text · builtAt · rev
```

**왜 기억이 md 파일이 아니라 테이블인가.** 내용은 자유 평문이 맞다 — 다음에 무슨 사실이
올지 모르니 스키마를 잡을 수 없고, 계산에 쓰이지도 않는다. 하지만 **파일로 두면 한 줄만
고쳐도 전체 재작성**이고, 자동 저장 중 크래시하면 통째로 깨지며, 백업 스냅샷·복원 경로를
DB와 파일 두 벌로 관리해야 한다. 행으로 두면 부분 수정·삭제·타임스탬프·백업 병합이 공짜다.

**규칙: 계산에 들어가는 값은 컬럼, 모델이 읽기만 하는 서술은 평문 한 줄.**
예를 들어 체중은 `TargetCalculator`가 목표 칼로리를 계산하는 데 쓰므로 `body_record`의
컬럼으로 남는다. "키 175cm"는 지금 아무 계산에도 안 쓰이므로 기억 한 줄이면 된다.
나중에 TDEE 공식을 정밀화해 키를 쓰게 되면 그때 컬럼으로 승격한다.

### 백업에 무엇을 싣나

| | 백업 포함 | 이유 |
|---|---|---|
| `ai_memory` | ✅ | 작고, 기기를 옮겨도 코치가 나를 알아봐야 함 |
| `chat_session` / `chat_message` | ❌ **항상 제외** | 아래 |
| API 키 | ❌ **절대** | 같은 이유 |

**대화를 백업에 넣지 않는 이유**는 용량이 아니라 **이 파일이 남에게 주는 파일이기
때문**이다. 선택적 병합(`ROADMAP.md` 3번)이 남의 백업에서 루틴만 골라 오는 기능이라,
실제로 파일을 주고받게 되어 있다. 대화가 들어 있으면 루틴 하나 공유하려다 무릎 통증
얘기, 체중 고민까지 통째로 넘어간다. 옵션으로 두면 켜둔 걸 잊고 공유하는 날이 온다.
**켤 수 없게 만드는 것이 유일하게 확실한 방법이다.**

### 대화는 텍스트로 따로 내보낸다

대신 대화를 **읽을 수 있는 텍스트로 뽑는 경로**를 둔다. 백업과 목적이 다르다 —
백업은 앱이 되읽는 것이고, 이건 사람이 읽거나 다른 곳에 옮겨 붙이는 것이다.

- 단위는 **세션 하나 = 파일 하나**. 대화 화면 메뉴에서 바로 내보낸다
- 형식은 **Markdown**. 어디에 붙여도 읽힌다
- 담는 것: 날짜, 쓴 모델, 대화 원문(질문·답변)
- **주입된 컨텍스트(L0~L2)는 기본으로 빼고**, 필요하면 체크해서 포함한다. 길고,
  기억과 신체 수치가 그대로 들어 있다
- 내보낸 파일은 앱 밖으로 나가므로, 공유 시트로 넘길 때 한 번 알린다

```markdown
# 하체 루틴 상담 — 2026-09-06
모델: anthropic/claude-sonnet-5 (OpenRouter)

**나**  이번 주 하체 볼륨 어때?
**AI**  최근 7일 하체 세트가 32개고 볼륨은 12,400kg입니다. …
```

## 5. 컨텍스트 파이프라인

### 5.1 다섯 층으로 쌓는다

```
┌─ 세션 동안 안 변함 ────────────────────┐
│ L0  정적 규칙 (도메인·응답 규칙)  ~400 │
│ L1  기억 (ai_memory 렌더링)       ~200 │  ← 프롬프트 캐시가 걸리는 구간
│ L2  매니페스트 + 요약 통계        ~400 │
└──────────── 캐시 경계 ────────────────┘
  L3  대화 이력 (최근 N턴)          ~800
  L4  오늘 날짜·시각 + 이번 질문     ~50
```

**날짜·시각은 반드시 캐시 경계 뒤에 둔다.** 시스템 프롬프트 앞쪽에 현재 시각을 넣으면
매 요청 프리픽스가 달라져 캐시가 통째로 무효가 된다. 캐싱을 껐다 켰다 하는 것보다
더 나쁜 건, **에러 없이 조용히 안 걸리는 것**이다.

### 5.2 왜 세션 시작에 굳히나

L1·L2를 매 턴 다시 계산하면 반올림 하나로 문자열이 흔들리고 캐시가 깨진다. 그래서
**챗을 열 때 한 번 만들어 `ai_context_cache`에 굳히고, 그 세션 동안 그대로 쓴다.**

대화 도중 사용자가 오늘 운동을 고쳐도 그 세션의 요약은 옛 상태로 남는다. 이게 문제가
되는 경우("방금 추가한 종목을 왜 몰라?")는 도구 호출로 최신을 읽어오면 되고, 그 편이
매 턴 캐시를 깨는 것보다 싸다.

### 5.3 L0 — 정적 규칙

안 변하는 것만. 코드에서 만들 수 없는 **도메인 규칙**이 핵심이다.

- 매크로가 `null`이면 *모름*, `0`이면 *진짜 0* — 둘은 다르다
- 체지방률이 비어 있으면 체중·체지방량에서 계산된 값이다
- 끼니 이름은 고정 슬롯이 아니라 사용자가 자유롭게 붙인다
- 세트의 `done=false`는 계획만 하고 안 한 세트다
- **관찰(§6.2)은 그 시점의 발언이지 확정된 사실이 아니다.** 오래됐거나 한 번뿐인
  관찰로 단정하지 말 것
- **데이터가 없으면 없다고 답하는 것이 옳은 답변이다**
- 간결하게 답한다 (출력 토큰이 입력의 5배 비싸다)

> **함정**: 스키마 설명을 손으로 쓰지 말 것. md에 적은 필드가 실제 스키마와 어긋나면
> AI가 없는 필드를 근거로 추론하는데, 조용히 틀리는 종류라 발견이 늦다.
> **스키마 부분은 코드에서 생성**하고, 손으로 쓰는 건 위 같은 도메인 규칙만.

### 5.4 L2 — 매니페스트와 요약

데이터를 통째로 넣지 않고 **데이터의 지도**를 넣는다. JSON이 아니라 줄 단위 평문으로 —
중괄호와 따옴표와 키 이름이 전부 토큰이다.

```
기록 2026-01-03~2026-09-06 (247일 중 189일, 58일 공백)
목표 벌크업·활동량 보통 / 2,600kcal 단백질 165g
체중 74.3kg (09-05 인바디) 30일 +0.8kg · 체지방 15.1%
운동 최근 7일 4회 · 볼륨 34,200kg
  부위별 세트: 하체 32 · 등 24 · 가슴 21 · 어깨 15 · 팔 12 · 코어 9
  주요 최고중량: 레그프레스 60kg / 벤치머신 45kg / 랫풀다운 50kg
식단 최근 7일 평균 2,480kcal 단백질 158g (입력 5일 · 추정 1일 · 미기록 1일)
종목 카탈로그 50개 · 음식 카탈로그 63개 · 루틴 5개
※ 세트/끼니 상세는 이 대화에 없음. 필요하면 조회 도구를 쓸 것
```

**있다는 사실과 지금 못 읽는다는 사실을 같이 적는다.** "벤치 41세션"만 적으면 내용이
있다는 뉘앙스라 모델이 채워 넣는다. 경계를 같이 주면 "모른다"에서 한 걸음 더 나아가
*"조회해볼까요?"* 로 간다.

### 5.5 토큰 예산

| 층 | 상한 |
|---|---|
| L0 + L1 + L2 | 1,200 토큰 |
| L3 대화 이력 | 1,500 토큰 (넘으면 오래된 것부터 요약으로 접기) |
| 출력 | 800 토큰 |

상한을 코드에 상수로 두고 **테스트로 지킨다**(§10). 안 그러면 요약에 항목을 하나씩
더하다가 어느 날 대화 한 번에 5,000 토큰을 쓰게 된다.

넘칠 때의 처리는 업계에서 정착된 4단을 그대로 쓴다:

1. **우선순위** — L0·L1·L2는 절대 안 자른다 (자르면 답의 근거가 사라진다)
2. **슬라이딩 윈도우** — 최근 N턴만 원문으로
3. **요약 접기** — 밀려난 턴은 한 덩어리 요약으로 대체
4. **하드 컷** — 그래도 넘치면 오래된 요약부터 버리고, **버렸다는 사실을 화면에 표시**

4번을 조용히 하면 "아까 말한 거 왜 잊었어?"가 된다. 잘랐으면 잘랐다고 말해야 한다.

**요약할 때 무엇을 남길지 지시한다.** 요약은 손실 압축이라 아무거나 남기면 뼈대가 날아간다.
남길 것은 **목표·제약·수치·사용자 선호**, 버릴 것은 인사말과 이미 답이 끝난 질문이다.

> **어차피 자를 층은 L3뿐이라는 걸 기억할 것.** 오래 가야 하는 맥락은 애초에 L3에 두면
> 안 된다 — 앱이 아는 것(목표·기록·체중)은 L2로 매번 들어가고, 대화에서 나온 오래 갈
> 맥락(부상·장비·선호)은 **기억으로 승격**시켜 L1으로 올린다(§6.2). 승격 제안이 단순한
> 편의 기능이 아니라 **휘발되는 층에서 안 휘발되는 층으로 옮기는 동작**인 이유가 이것이다.
> 요약 접기는 그 둘에 해당하지 않는 임시 맥락("이번 주는 출장이라 헬스장 못 감")을
> 위한 완충이지, 장기 기억의 대체재가 아니다.

## 6. 기억

### 6.1 무엇을 담나

기록으로 표현할 수 없는 것만. **앱 데이터와 중복되면 안 된다** — 체중은 `body_record`가
진실이고, 기억에 "체중 74kg"을 적으면 둘이 어긋나는 날이 온다.

담는 것: 부상·제약("무릎이 안 좋아 백스쿼트 대신 레그프레스"), 장비·환경("집엔 덤벨만"),
선호("닭가슴살은 질림"), 일정("화·목 저녁만"), 목표 배경("10월 결혼식"), 코칭 톤 선호.

### 6.2 확정과 관찰을 나눈다

기억이 위험해지는 건 자동으로 저장해서가 아니라 **해석해서 압축**하기 때문이다.
"오늘은 무릎이 좀 시큰해서 가볍게 했다"를 `무릎 부상`으로 줄이면 날짜도 정도도 사라지고,
석 달 뒤에도 그 단정문이 모든 루틴 제안을 묶는다.

그래서 두 종류로 나눈다.

| | 확정 (`FACT`) | 관찰 (`OBSERVATION`) |
|---|---|---|
| 저장 | 사용자가 "기억해줘" 하거나, 모델 제안을 **승인**했을 때 | 모델이 뽑으면 **자동** |
| 형태 | 정리된 문장 | **원문 그대로 + 날짜** |
| 수명 | 사용자가 지울 때까지 | 90일 지나면 빠짐 |

프롬프트에는 이렇게 나뉘어 들어간다:

```
## 확정 (사용자가 승인함)
- 집엔 덤벨만 있고 헬스장은 화·목
- 닭가슴살은 질려서 못 먹음

## 관찰 (참고용, 확정 아님)
- 09-06 "무릎이 시큰해서 가볍게 했다"
- 08-14 "무릎 좀 아픔"
```

그리고 L0 규칙에 못 박는다: **관찰은 그 시점의 발언이지 확정된 사실이 아니다. 오래됐거나
한 번뿐인 관찰로 단정하지 말 것.** 원문과 날짜가 남아 있으면 모델이 알아서 강도를 조절한다
— "한 달 전에 무릎이 시큰하다고 하셨는데 요즘은 어떠세요?" 정도로 나오고, 부상으로
단정하지 않는다. 단정할 재료가 안 들어갔기 때문이다.

**같은 주제의 관찰이 쌓이면 승격을 제안한다.** "무릎 관련 언급이 3번 있었어요. 제약으로
등록할까요?" → 승인하면 확정으로 올라간다. 한 번 시큰한 것과 만성 통증이 이 경로로 갈린다.

### 6.2-1 담을 수 있는 갈래를 미리 정해둔다

LibreChat은 저장 가능한 키를 `validKeys`로 제한한다 — 아무거나 저장되지 않게 하는 장치다.
같은 이유로 우리도 갈래를 고정한다: **부상·제약 / 장비·환경 / 음식 선호 / 일정 / 목표 배경 /
코칭 톤**. 여기에 안 맞으면 저장하지 않는다.

그리고 **갈래마다 갱신(upsert)한다.** 같은 주제를 다시 말했는데 줄이 하나 더 쌓이면
기억이 금세 중복으로 불어나고, 서로 모순되는 두 줄이 같이 주입되는 일이 생긴다.
확정 기억은 갈래 단위로 덮어쓰고, 관찰은 원문 보존이 목적이므로 쌓되 90일에 빠진다.

### 6.2-2 추출은 매 요청마다 하지 않는다

LibreChat은 메모리 에이전트를 **매 채팅 요청마다** 돌리는데, 자기 문서에서 이걸 한계로
적어두고 있다(비용). Open WebUI는 반대로 백그라운드 리뷰를 **기본 끄고** N턴마다 돈다.

우리는 **세션이 끝날 때 또는 6턴마다 한 번** 추출한다. 추출도 결국 API 호출이라 매 턴
돌리면 대화 비용이 두 배가 된다. 사용자가 "기억해줘"라고 말한 턴은 예외로 즉시 처리한다.

### 6.3 관리

- 상한 **확정 40줄 / 관찰 20줄, 합쳐 600토큰**. 넘으면 오래되고 안 쓰인 것부터
  사용자에게 정리를 제안한다
- 관찰이 저장되면 대화에 **"기억해뒀어요"를 눈에 보이게** 표시한다. 조용히 쌓이면
  나중에 이유 모를 답변이 나온다
- **기억 화면**에서 전부 보고 고치고 지울 수 있어야 한다. 매 요청 외부로 전송되는
  개인 건강정보다 — 사용자가 목록을 통제하지 못하면 안 된다
- 기억 기능 자체를 **끌 수 있게** 한다

## 7. 환각 방지

이 기능의 품질 기준이다. 프롬프트에 "지어내지 마"라고 쓰는 것으로는 부족하고,
**구조적으로 지어낼 여지를 없애는 쪽**이 확실하다.

### 가) 값마다 출처를 붙인다

이 앱은 `MacroEstimator`의 어림값과 사용자가 직접 넣은 값이 섞인다. 구분 없이 넘기면
**추정치가 사실로 세탁된다.**

```
점심 김밥 1줄        520kcal (estimated)
저녁 닭가슴살 200g   330kcal (entered)
아침 —              (모름)
```

> **DB 11에서 해결됨.** `meal_entry.macroSource`가 `ENTERED` / `CATALOG` / `ESTIMATED` /
> `NONE`을 구분한다. 다만 **마이그레이션 이전에 쌓인 기록은 전부 `ENTERED`**다 —
> 그 안에 확정된 어림값이 섞여 있어도 지금 와서는 갈라낼 수 없다. L0 규칙에
> "2026-09-06 이전 기록의 출처 표기는 신뢰할 수 없다"를 적어 그 경계를 알린다.

### 나) 빈 곳을 숫자로 명시한다

"247일 중 189일, 58일 공백". 이걸 안 주면 평균을 낼 때 빠진 날을 모르고 계산한다.

### 다) 주입한 것을 화면에 그대로 보여준다

접을 수 있는 **"이 대화에 포함된 데이터"** 패널. 사용자가 AI의 말과 실제 주입 내용을
직접 대조할 수 있다. 답변의 숫자를 자동 대조하는 검증도 검토했으나 보류 — 평균·증감처럼
정당하게 계산된 숫자가 오탐으로 잡혀 실용성이 없다.

## 8. 도구 사용 (2·3단계)

모델은 DB에 접근하지 못한다. "이 함수를 이 인자로 불러달라"는 **구조화된 요청을 뱉을 뿐**,
실행은 앱이 한다. 그래서 위험한 동작에 확인 UI를 끼워 넣을 수 있다.

### 2단계 — 읽기 도구

| 도구 | 인자 | 돌려주는 것 |
|---|---|---|
| `getWorkouts` | from, to, exerciseName? | 날짜별 종목·세트 (상한 있음) |
| `getMeals` | from, to | 날짜별 끼니·매크로·출처 |
| `getBodyRecords` | from, to | 측정 기록 |
| `getExerciseHistory` | exerciseSlug, limit | 그 종목의 최고중량·볼륨 추이 |

**모든 도구에 반환 상한을 둔다.** 6개월치 세트를 통째로 돌려주면 컨텍스트가 터지고
비용도 폭발한다. 넘치면 잘라내고 "잘렸다"는 사실을 같이 돌려준다.

### 3단계 — 쓰기 도구

`addMeal` · `addWorkoutSet` · `saveBodyRecord`. **항상 확인 UI를 거친다** — 모델이 요청하면
앱이 "이렇게 기록할까요?" 카드를 띄우고, 사용자가 눌러야 실제로 저장된다. 자동 실행은 없다.

## 9. 비용 · 모델 선택

과금은 입력 + 출력 토큰이다. 대화가 길어질수록 매 턴 재전송하는 입력이 누적된다.

| 모델 | 입력 $/1M | 출력 $/1M | 쓰임 |
|---|---|---|---|
| Claude Opus 5 | $5 | $25 | 루틴 재설계 같은 상담 |
| Claude Sonnet 5 | $2 | $10 | 기본값 후보 |
| Claude Haiku 4.5 | $1 | $5 | "이번 주 단백질 평균" 류 |

*(2026-06-24 기준. 구현 시 각 사 가격 페이지로 재확인)*

우리 예산(입력 ~2,300 · 출력 ~400) 기준 한 턴에 **Opus 5 ≈ 30원, Haiku 4.5 ≈ 6원**.

**프롬프트 캐시**는 재전송되는 프리픽스 값을 약 1/10로 낮춘다(쓸 때 1.25배). 5분 TTL
기준 **두 번째 요청부터 이득**이라 챗에서는 거의 항상 이득이다. 단 모델마다 최소 캐시
프리픽스(512~4,096토큰)가 있어서 우리 프리픽스가 짧으면 **조용히 안 걸린다.**
응답의 `cache_read_input_tokens`가 0이 아닌지 반드시 확인할 것.

**가장 큰 절약은 출력을 줄이는 것**이다(출력이 입력의 5배). 그래서 L0에 "간결하게" 규칙이
들어 있고, 그 다음이 모델 선택, 그 다음이 컨텍스트 압축이다.

## 10. 테스트 전략

API를 실제로 부르는 테스트는 만들지 않는다(돈이 들고 결과가 매번 다르다). 대신
**앱이 만든 것**을 검증한다.

- **컨텍스트 빌더의 결정론**: 같은 DB 상태 → 항상 같은 문자열. 캐시 프리픽스가 흔들리면
  프롬프트 캐시가 죽으므로 이건 성능이 아니라 정확성 문제다
- **토큰 예산 상한**: 요약이 상한을 넘으면 실패. 항목을 늘리다 조용히 비싸지는 걸 막는다
- **출처 표기**: 추정 매크로가 `entered`로 새어 나가지 않는지
- **빈 구간 표기**: 공백 일수가 실제와 맞는지
- **도구 반환 상한**: 큰 기간을 요청해도 상한에서 잘리고 잘렸다고 알리는지
- **기억 CRUD + 상한**
- **마이그레이션 10 → 11** (기존 기록이 살아남는지)
- **프로바이더 어댑터**: 저장해둔 응답 샘플(JSON/SSE)을 파싱해 우리 타입으로 옮기는지

## 11. 실패 처리

| 상황 | 동작 |
|---|---|
| 키 없음 | 챗 화면이 설정으로 안내. 호출 시도 안 함 |
| 키 무효(401) | "키를 확인하세요" + 설정 바로가기. 재시도 안 함 |
| 사용량 초과(429) | 잠시 후 재시도 안내. 자동 재시도는 1회까지 |
| 네트워크 끊김 | 지금까지 받은 부분 응답을 **저장하고** "중단됨" 표시 |
| 스트리밍 중 앱 백그라운드 | 진행 중인 응답을 취소하지 않고 받은 데까지 저장 |
| 컨텍스트 초과 | 오래된 턴부터 접어서 재시도, 그래도 넘치면 새 세션 권유 |

## 12. 프라이버시

- **API 키는 `EncryptedSharedPreferences`** (Android Keystore 기반). Room·백업 파일에
  절대 넣지 않는다
- **⚠️ Auto Backup에서 반드시 제외한다.** 이 앱은 지금 `android:allowBackup="true"`이고
  제외 규칙이 없다. 그대로 두면 암호화된 키 파일이 구글 백업에 실려 새 기기로 복원되는데,
  **복호화 키(Keystore)는 기기를 넘어가지 않아서** 복원 직후 읽기가 실패한다.
  라이브러리에 따라 예외가 아니라 크래시로 나타난다. `dataExtractionRules`(API 31+)와
  `fullBackupContent`에 제외 규칙을 넣고, 키가 없으면 "다시 입력해 주세요"로 흐르게 한다
- 매 요청에 **개인 건강정보가 외부로 나간다**. 챗을 처음 켤 때 무엇이 전송되는지
  화면으로 알리고, "이 대화에 포함된 데이터" 패널로 항상 확인 가능하게 한다
- **프로바이더를 바꾸면 같은 데이터가 다른 회사로 간다.** 전환 시 한 번 고지한다
- 백업 파일에 대화 로그를 기본으로 넣지 않는다(§4)

## 13. 만드는 순서

**1단계 — 읽기 전용 챗**
설정 화면(프로바이더·키·모델) → `AiProvider` 인터페이스 + Claude 어댑터 → 챗 화면(스트리밍)
→ 컨텍스트 빌더(L0~L4) + 예산 테스트 → 대화 저장 → "포함된 데이터" 패널
→ **기억은 확정(명시적 저장)만**

*완료 기준*: "이번 주 하체 볼륨 어때?"에 주입된 요약만으로 정확히 답하고,
데이터 없는 질문에 "기록이 없다"고 답한다.

**2단계 — 도구 조회 + 관찰 기억**
읽기 도구 4종 + 상한 → 도구 호출 루프 → 관찰 자동 저장(원문·날짜) + 승격 제안
→ 기억 관리 화면 → 나머지 두 프로바이더 어댑터

*기억 쪽 완료 기준*: 한 달 전 "무릎이 시큰"이라고 한 대화가 있으면 단정하지 않고
그 시점을 짚어 되묻는다.

*완료 기준*: "6월 벤치 세트 보여줘"에 도구를 호출해 답하고, 잘린 경우 잘렸다고 말한다.

**3단계 — 쓰기 + 다듬기**
쓰기 도구 3종 + 확인 카드 → 대화 요약 접기 → 모델별 비용 표시

## 15. 참고한 오픈소스 사례

같은 문제(BYOK 챗 + 기억 + 컨텍스트 관리)를 이미 푼 것들을 보고 §3·§5·§6·§12를 고쳤다.

| 사례 | 배운 것 |
|---|---|
| [Open Chat](https://openchat.codes/) (Android, BYOK) | 어댑터 하나(OpenAI 호환)로 8개 프로바이더. 키는 Android Keystore, 대화는 기기에만 → §3.1 |
| [LibreChat](https://www.librechat.ai/docs/features/memory) | 기억을 **key/value + 갈래 제한(`validKeys`)**, 토큰 상한(기본 2000). 메모리 에이전트를 매 요청 돌리는 걸 **스스로 한계로 명시** → §6.2-1, §6.2-2 |
| [Open WebUI](https://docs.openwebui.com/features/chat-conversations/memory/) | 기억 주입 on/off를 **기능과 분리**, 사용자가 전부 열람·삭제, 백그라운드 추출은 **기본 끔 + N턴마다** → §6.2-2, §6.3 |
| [OpenRouter BYOK](https://openrouter.ai/docs/use-cases/byok) | 키 하나로 다중 모델. 대신 중개자를 한 번 더 지난다 → §3.1의 트레이드오프 |
| 컨텍스트 관리 정론 | 우선순위 → 슬라이딩 윈도우 → 요약 → 하드 컷의 4단 조합 → §5.5 |
| [EncryptedSharedPreferences + Auto Backup](https://issuetracker.google.com/issues/176215143) | 백업에서 제외하지 않으면 **기기 복원 시 복호화 실패·크래시** → §12 |

**차별점으로 남긴 것**: 위 사례들은 기억을 전부 "요약된 사실"로 압축한다. 우리는 관찰을
**원문+날짜 그대로** 남긴다(§6.2) — 한 번 시큰한 무릎이 "무릎 부상"으로 굳는 실패를
막는 게 이 앱에선 더 중요하다. 그 대신 확정 기억만 갈래별로 압축·갱신한다.
