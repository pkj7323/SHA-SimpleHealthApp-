# 식단 개편 설계 — 음식을 g 단위로

`ROADMAP.md`가 "무엇을 할지"라면 이 문서는 **"어떻게"** 를 정한다. `AI-CHAT-DESIGN.md`보다
먼저 만든다 — AI가 식단에 쓸모 있으려면(추천·기록·집계) 구조화된 음식 데이터가 먼저
있어야 한다.

목표: **끼니가 음식 줄의 합이 되게 한다.** 참고 삼은 화면은 인아웃 — 음식 하나를 고르면
1인분 표시(`공기 210g`)와 배수 입력, g 직접 입력이 같이 뜨고 매크로는 계산된다.

---

## 결정 요약

| 항목 | 결정 |
|---|---|
| 끼니의 구성 | `meal_entry`(끼니) 아래 `meal_food`(음식 줄) 여러 개. 매크로는 **계산값** |
| 음식 카탈로그 | `food_item`이 **음식 하나당 기준 그램 하나**(`baseAmountGram`)를 갖는다. 100g 환산도, 제공 단위 여러 개도 아니다 |
| 수량 입력 | **배수만** 입력(1.5배처럼). 기준 그램을 알면 결과 그램도 같이 보여줌 |
| 그램 모르는 음식 | `baseAmountGram = null`. 배수 입력만 하고 총 그램은 표시 안 함 — **숫자를 지어내지 않는다** |
| 순서 조정 | **된다.** 운동 종목과 같은 방식으로 `orderIndex` + ↑↓ |
| 기존 자유 텍스트 끼니 | **그대로 둔다.** 새 구조로 자동 변환하지 않는다 (아래 §3) |
| 카탈로그 출처 | AI가 제안해도 `food_item.source`는 그냥 `USER`. 신뢰도 구분은 `meal_food.macroSource`에서만 |
| 스키마 | DB 12 (`meal_food`, `food_item`/`meal_entry` 개편) |

## 1. 왜 지금 구조로는 안 되나

지금 한 끼니는 자유 텍스트 한 덩어리다.

```
menuText = "현미밥 180g + 닭가슴살 150g + 나물반찬"
kcal = 720, protein = 45 ...   ← 사람이 총합을 직접 잰 값
```

`food_item`(음식 카탈로그)은 입력을 돕는 도우미일 뿐이다. "음식 목록에서 고르기"를 누르면
그 값이 끼니 칸에 **복사**되고 연결은 안 남는다. 그래서 안 되는 것들:

- "이번 달 닭가슴살 몇 번 먹었어?" — 문자열 검색이라 "닭가슴살"과 "닭가슴살 스테이크"가
  안 갈린다
- "단백질의 몇 %가 닭가슴살에서 왔어?" — 불가능. 끼니 안의 음식이 안 나뉜다
- "150g을 200g으로 바꾸면?" — 끼니 전체를 다시 입력해야 한다
- AI가 "오늘 점심 닭가슴살 200g 기록해줘"를 정확히 실행할 수 없다 — 얼마짜리 값을
  써야 할지 카탈로그에 없다

## 2. 구조

```
food_item          name "닭가슴살" · baseAmountGram(nullable) · 그 기준량당 kcal·탄·단·지·당

meal_entry (끼니)   date · slotName · eaten · memo · orderIndex(끼니 순서, 기존)
   └ meal_food     foodId? · name(스냅샷) · orderIndex(음식 줄 순서)
                   · multiplier(배수) · amountGram(계산, nullable)
                   · macros(계산된 스냅샷) · macroSource
```

`food_serving`처럼 음식마다 프리셋을 여러 개 두지 않는다. **음식 하나당 기준량은 하나**고,
화면에서 조절하는 건 배수뿐이다(`× 1.5`). 스크린샷의 "공기(210g)" + 배수 입력이 이 모양이다
— 다만 이 앱은 음식마다 단위 하나만 있으면 되므로 그 이상의 선택지(공기/g 전환 등)는
만들지 않는다.

**계산 결과를 끼니에 스냅샷으로 저장한다.** 카탈로그 값을 나중에 고쳐도 과거 기록이
흔들리면 안 된다 — 운동 기록이 `trackingType`을 그 시점 값으로 복사해두는 것과 같은 이유다
(`WorkoutExercise.trackingType`).

`foodId`는 nullable이다. 카탈로그 항목이 지워져도 과거 기록의 `name`·`macros`는 남는다
(`WorkoutExercise.exerciseName`과 같은 패턴).

**순서 조정이 된다.** `meal_food.orderIndex` + 운동 종목과 같은 ↑↓ 버튼. 끼니 안에서
음식을 원하는 순서로 옮길 수 있다(저장 순서는 화면 표시 순서와 무관하므로 자유롭게 바꿔도
데이터가 안 꼬인다 — `toPersistables`가 리스트 순서로 다시 매기는 것과 같은 방식).

### 2.1 왜 기준 그램이 nullable인가

시드 음식 상당수는 지금 `"김밥 1줄"`, `"라면 1봉"`처럼 **실제 그램을 모른다.** 여기서
"1줄 = 230g"을 지어내면 이 앱이 §7(AI 챗 설계)에서 지키려던 원칙을 스키마 단계에서부터
어기는 셈이다.

그래서 `food_item.baseAmountGram`을 nullable로 둔다:

- 그램을 아는 것(닭가슴살 100g, 계란 1개 50g) → 배수를 조절하면 결과 그램(`amountGram`)도
  같이 계산돼 보인다
- 모르는 것(김밥 1줄) → **배수만** 입력받고 그램 관련 표시는 아예 안 한다. 매크로 계산은
  "1줄 몫 × 배수"라 그램을 몰라도 문제없다. 나중에 실제 그램을 알게 되면 그 값을
  채워 넣으면 그때부터 그램 표시가 열린다

### 2.2 매크로 출처가 여기서도 쓰인다

`MacroSource`(DB 11)에 갈래를 하나 더한다.

```kotlin
enum class MacroSource { NONE, ENTERED, CATALOG, ESTIMATED, AI_SUGGESTED }
```

- `meal_food`는 보통 `CATALOG`다 — 카탈로그 기준량 × 배수로 계산됐으니
- AI가 방금 만든 음식으로 기록하면 그 **끼니 줄에만** `AI_SUGGESTED` — 모델이 기억으로
  뱉은 숫자라 카탈로그 값과 같은 무게로 취급하면 안 된다. 다음에 같은 음식을 다시
  쓰면 이미 카탈로그에 있으므로 그때는 `CATALOG`로 기록된다
- 자유 텍스트 끼니(§3)의 직접 입력값은 그대로 `ENTERED`

**`food_item.source`에는 `AI` 값을 따로 만들지 않는다.** 종목이 그렇듯(`addUserExercise`는
누가 입력했든 `ItemSource.USER`), 카탈로그 단계에서는 "누가 만들었나"를 구분하지 않는다.
AI가 제안한 음식도 **사용자 확인을 거쳐 일반적인 "직접 추가"**로 카탈로그에 들어가고
(`ItemSource.USER`), 신뢰도 구분은 그 순간 기록되는 `meal_food.macroSource`에서만 한다.
이러면 `food_item`을 건드릴 필요가 없고 확인 흐름도 하나로 통일된다.

## 3. 기존 자유 텍스트 끼니는 그대로 둔다

파싱해서 `meal_food`로 쪼개지 않는다. `"현미밥 180g + 닭가슴살 150g + 나물반찬"`을
기계가 갈라 보면 반드시 틀린다 — 이 앱 전체가 "모르면 모른다고 하지, 틀리게 채우지
않는다"는 원칙으로 짜여 있다(`AI-CHAT-DESIGN.md` §1).

그래서 두 방식이 공존한다.

| | 옛 끼니 | 새 끼니 |
|---|---|---|
| 저장 | `menuText` 자유 텍스트 + 매크로 직접 입력 | `meal_food` 목록 |
| 매크로 | 사람이 총합을 입력 | 카탈로그에서 계산 |
| 편집 | 지금 화면 그대로 | 음식 추가/제거 |

`MealEntry`에 어느 쪽인지 표시하는 칸이 필요하다(`meal_food`가 하나라도 있으면 새 방식).
사용자가 옛 끼니를 새 구조로 다시 쓰고 싶으면 **직접 다시 입력**해야 한다 — 자동 변환은
하지 않는다.

## 4. 카탈로그 개편

### 4.1 시드 60여 개

이름에서 제공량을 뗀다. 예: `"닭가슴살 100g"` → 이름 `"닭가슴살"`, `baseAmountGram = 100`.
시드 데이터 자체에 이미 기준량이 적혀 있는 것들은 그대로 옮겨진다. `"김밥 1줄"`류는
이름만 `"김밥"`으로 바꾸고 `baseAmountGram`은 **비워둔다** — 실측하지 않은 값을 넣지 않는다.

시드 버전을 올려서 갱신한다(`SeedData.VERSION`). 기존 사용자의 `food_item`은 slug 기준
upsert라 사용자가 고친 값은 안 건드린다(기존 규칙 그대로).

### 4.2 사용자가 직접 만든 음식

기준량을 알 수 없다. **지금 입력한 값을 그대로 "1"의 기준으로 삼고**, `baseAmountGram`은
비워둔다 — 그램을 알아야 채울 수 있는데 모르기 때문이다. 필요하면 사용자가 나중에
그램을 채워 넣게 한다.

## 5. AI와 맞물리는 지점 (AI-CHAT-DESIGN.md와의 연결)

`AI-CHAT-DESIGN.md` §8은 종목처럼 음식도 "카탈로그에 없으면 새로 만들고, 확인 후 기록"
흐름을 쓴다.

```
"단백질 좀 더 채울 만한 거 추천해줘"
  → AI: "그릭요거트 150g 어때요? 대략 130kcal / 단백질 15g"
  → [카탈로그에 추가하고 오늘 저녁에 넣기]
  → 확인 카드 → meal_food 저장 (macroSource = AI_SUGGESTED)
```

이 구조가 있어야 §8의 쓰기 도구(`addMeal`)가 "무슨 음식을 몇 g"이라는 정확한 단위로
동작한다. 지금 자유 텍스트 구조로는 AI가 쓸 수 있는 게 문자열 붙이기뿐이었다.

그리고 이 개편이 `AI-CHAT-DESIGN.md` §14의 미결정 항목("음식 카탈로그 연결")의 답이다 —
스키마를 바꿔 해결하는 쪽으로 간다.

## 6. 만드는 순서

세 커밋으로 나눈다. 각각 계측 테스트를 통과한 뒤에만 다음으로 간다.

**1. 데이터 계층**
`meal_food` 엔티티 + `food_item.baseAmountGram` 추가 + DB 12 마이그레이션 + 시드
재작성(§4) + `MacroSource`에 `AI_SUGGESTED` 추가 + 매크로 계산 로직
(`기준 매크로 × multiplier`, `amountGram = baseAmountGram × multiplier`) + 테스트
(마이그레이션이 기존 `food_item`·자유 텍스트 끼니를 안 건드리는지, 계산이 맞는지).

**2. 음식 선택 · 수량 화면**
배수 스테퍼(+/-), 기준 그램이 있으면 결과 그램도 같이 표시. 그램 모르는 음식은
그램 표시 자체를 안 함.

**3. 끼니 화면 개편**
`meal_food` 목록 UI + 순서 조정(↑↓) + 옛 자유 텍스트 끼니와의 공존(§3) + 백업 포맷
(`MealFoodDto`) + xlsx 내보내기 반영.

## 7. 크라우드소싱은 하지 않는다 — 서버 없이 간다

"사람들이 많이 추가한 음식을 모아 다음 시드에 공식으로 반영하면 좋겠다"는 아이디어를
검토했다. **자동 수집을 하려면 서버가 필요하고, 이 앱의 정체성과 부딪힌다.**

- `SYNC-DESIGN.md`·`AI-CHAT-DESIGN.md` 둘 다 "서버 없이, 회원가입 없이"가 첫 줄이다.
  음식 사용 데이터를 자동으로 모으는 건 이 선을 처음으로 넘는 일이다
- 음식 기록은 건강정보라 민감하다. 자동 수집이면 동의 절차·프라이버시 정책·옵트인 UI가
  필요해지고, 인기순 집계 → 검수 → 시드 반영까지 이어지는 파이프라인은 별도 프로젝트급이다

**서버 없이도 같은 목적을 달성하는 경로가 이미 있다.** 이 앱엔 백업 내보내기와 선택적
병합이 있다 — 원하는 사용자가 자기 음식 목록을 백업 JSON으로 내보내 개발자에게 파일로
전달하면(깃허브 이슈 등), 개발자가 훑어보고 다음 버전 시드에 손으로 추가한다. **능동적으로
보내는 것**이라 동의 문제가 없고, 자동 집계는 못 하지만 이 앱 규모에서는 그걸로 충분하다.

지금은 이 수동 경로만 열어두고, 자동 집계·서버는 하지 않는다. 정말 필요해지면(사용자가
많이 늘어 시드가 눈에 띄게 부족해지면) 그때 별도로 논의한다.

## 8. 옛 끼니를 새 구조로 옮기는 방법 — 도구 없음

사용자가 옛 자유 텍스트 끼니를 새 구조로 다시 쓰고 싶으면, 끼니를 지우고 "음식 추가"로
처음부터 새로 입력한다. 원문을 띄워주는 도우미 화면 같은 건 만들지 않는다 — 화면 하나가
늘면 유지보수 비용이 생기는데, 옛 방식도 계속 정상 작동해서 이 전환에 실제 수요가
있는지부터 써보며 확인하는 게 먼저다. 나중에 불편하다는 게 분명해지면 그때 추가한다.

## 9. 화면 재구성 — 인아웃 참고

3단계가 붙은 뒤 인아웃(비슷한 다이어트 앱)의 화면 구조를 참고해서 몇 가지를 더 정했다.

### 9.1 끼니 4개 고정

지금까지는 "끼니 추가"로 사용자가 원하는 만큼 만드는 구조였다. **아침·점심·저녁·간식
4개를 기본으로 항상 띄워둔다** — 그날 처음 여는 순간부터 보이고, 아무것도 안 건드리면
DB에 저장되지 않는다(자동 저장은 편집이 있을 때만 돈다). 5번째 끼니(야식 등)가 필요하면
지금의 "끼니 추가" 버튼을 그대로 작게 남겨서 쓴다 — 기본 4개는 고정, 그 이상은 자유.

### 9.2 즐겨찾기

`FoodItem.favorite: Boolean = false` 컬럼 하나. 자주 쓰는 음식을 검색해서 찾는 대신
즐겨찾기 탭에서 바로 고른다. 카탈로그 시드·사용자 등록 음식 모두에 붙는다.

### 9.3 식사세트 ("내 식사")

인아웃 자체 용어로는 "내 식사". **자주 먹는 조합을 저장해뒀다가 한 번에 다시 담는다** —
"닭가슴살 150g + 현미밥 200g + 브로콜리 100g"을 매번 세 번 검색하는 대신 "다이어트
도시락" 하나로 저장해두고 한 번에 끼니에 넣는다. 후기를 보면 실제로 반응이 좋은 기능이라
(§검색 결과) 만들 가치가 있다.

**`DietTemplate`(식단표)과는 다른 단위다.** 식단표는 하루 전체(여러 끼니)의 틀이고,
식사세트는 **끼니 하나에 들어가는 음식 조합**이다. 그래서 별도 테이블이 필요하다.

```
meal_preset        id · name · orderIndex
meal_preset_food   id · presetId · orderIndex · foodId? · name · multiplier
                   · amountGram · macros · macroSource
```

`meal_food`와 거의 같은 모양이다. 담을 때는 `foodId`가 살아 있으면 **그 순간 카탈로그
값으로 다시 계산**하고(값이 바뀌었을 수 있으니), 카탈로그에서 지워졌으면 저장해둔
`macros` 스냅샷으로 대체한다 — AI가 제안한 음식이 카탈로그 없이도 기록되는 것과 같은
처리다.

저장은 끼니 카드에 "이 조합을 세트로 저장" 버튼을 하나 더 둬서, 지금 담긴 음식 줄
그대로를 `meal_preset`에 옮긴다("식단표로 저장"과 같은 자리, 한 단계 아래 단위).

### 9.4 레시피는 만들지 않는다

인아웃의 "레시피"는 실제 조리법(재료·조리 단계)이다. 이 앱은 조리를 다루지 않고
"뭘 얼마나 먹었나"만 기록하므로 이 앱 성격과 안 맞는다. 만들지 않는다.

### 9.5 AI 검색 토글 — 자리만 만들어둔다

음식 추가 화면에 "일반 검색 / AI 검색" 토글을 넣는다(누르면 배경색이 바뀌는 스타일).
**AI 검색은 지금 누르면 "준비 중" 안내만 뜬다** — `AI-CHAT-DESIGN.md`의 백엔드가 아직
없기 때문이다. 자리를 미리 만들어두는 이유는 나중에 AI 챗을 붙일 때 화면을 새로 짤
필요 없이 그 안내 자리만 실제 검색으로 바꾸면 되게 하려는 것이다.

### 9.6 직접 등록을 목록 맨 위에 고정

지금까지는 카탈로그에 없는 음식을 등록하는 화면이 없었다(운동 종목엔 있었다 —
`addUserExercise`). 음식도 같은 걸 만들어서, 검색 결과 목록 맨 위에 "직접 등록"을
고정해둔다. 이름 + 매크로 + (아는 경우) 기준 그램을 받는다 — 종목의 "직접 추가"와
같은 흐름이다.

### 9.7 만드는 순서

**1. 스키마** — `FoodItem.favorite`, `meal_preset`/`meal_preset_food`, 음식 직접 등록
함수(`addUserFood`) + DB 13 마이그레이션 + 테스트.

**2. 화면** — 음식 추가 다이얼로그를 탭 구조(즐겨찾기 / 식사세트 / 검색)로 재구성,
AI 검색 토글(비활성), 직접 등록 다이얼로그, 즐겨찾기 토글 버튼, "이 조합을 세트로 저장".

**3. 끼니 4개 고정** — 빈 날짜를 열면 아침/점심/저녁/간식을 기본으로 채우고, 5번째부터는
기존 "끼니 추가"로.
