# 저장 · 동기화 설계

`ROADMAP.md`가 "무엇을 할지"라면 이 문서는 저장/동기화의 **"어떻게"** 를 정한다.

목표: **폰과 PC에서 같은 기록을 본다.** 서버 없이, 회원가입 없이.

---

## 결정 요약

| 항목 | 결정 |
|---|---|
| 동기화 단위 | **gzip JSON 스냅샷** (DB 파일 아님) |
| 저장소 | 드롭박스 앱 전용 폴더 |
| 시점 | 앱 열 때 받기 / 앱 내릴 때 올리기 |
| 충돌 | 드롭박스 `rev`로 **사전 감지**, 자동 병합 안 함 |
| 업로드 실행 | **WorkManager** (프로세스 종료에도 살아남음) |
| WAL | **그대로 켜둠** (끌 필요 없음) |
| 레코드 단위 병합 | **안 함** (아래 "왜 안 하는가") |

## 1. 왜 DB 파일이 아니라 JSON인가

처음엔 DB 파일 하나를 통째로 올리고 받는 안을 잡았는데, 코드를 보고 뒤집었다.

### 결정적 이유 — 스키마 버전 어긋남

파일 통째 동기화는 **두 기기의 앱 버전이 항상 같아야** 성립한다. 실제로는 이렇게 깨진다:

1. 폰 앱 업데이트 → DB 버전 6
2. 폰이 v6 DB를 올림
3. PC 앱은 아직 v5 → v6 파일을 열면 **Room은 다운그레이드 마이그레이션을 지원하지 않는다**

두 앱을 항상 동시에 업데이트해야 하는데 그걸 잊는 게 정상이고, 이 실패는 조용하지 않다 — 크래시나 데이터 손상으로 나타난다.

JSON은 견딘다. 모르는 필드는 무시하고, 없는 필드는 기본값으로 채우면 된다.

### 두 번째 이유 — 3번(JSON 공유/백업)과 코드가 같다

로드맵 3번에서 JSON 내보내기/가져오기를 어차피 만든다. DB 파일 동기화를 따로 만들면 **전송 메커니즘을 두 벌** 만드는 셈이다. 같은 직렬화 코드를 쓰면 동기화는 "그 JSON을 드롭박스에 올리고 받는 것"이 전부다.

### 비교

| | DB 파일 | JSON 스냅샷 |
|---|---|---|
| 스키마 버전 어긋남 | **깨짐** (다운그레이드 불가) | 견딤 |
| 3번과 코드 공유 | 없음 | **전부 공유** |
| 디버깅 | 불가(바이너리) | 열어서 눈으로 확인 |
| 나중에 부분 병합 | 불가 | 가능 |
| 구현 난이도 | 파일 복사라 쉬움 | 왕복이 무손실이어야 함 |

데이터 양은 문제가 안 된다. 몇 년치 기록이라도 JSON 몇 MB, gzip하면 수백 KB.

### 딸려오는 이득 — WAL을 끌 필요가 없어졌다

로드맵 0-2단계(`journal_mode = DELETE`)의 목적은 **오직** "파일을 복사할 때 `-wal`/`-shm`으로 쪼개져 깨지는 걸 막는 것"이었다. 파일을 안 만지면 그럴 일이 없다. **WAL을 켜둔 채 성능 이점을 유지한다.**

> 참고: `VACUUM INTO`로 일관된 스냅샷을 뜨는 방법도 검토했으나, SQLite 3.27+가 필요해 **minSdk 26**(SQLite 3.19)에서는 못 쓴다. JSON을 택하면서 이 문제도 같이 사라졌다.

### 대신 지켜야 할 것 — 왕복 무손실

JSON의 유일한 약점은 **직렬화가 필드를 빠뜨리면 동기화할 때마다 조용히 데이터가 사라진다**는 점이다. 파일 복사엔 없는 위험이라 반드시 막아야 한다.

→ **왕복 테스트를 필수로 둔다.** `내보내기 → 가져오기 → 다시 내보내기` 결과가 처음과 완전히 같은지 자동 검증. 엔티티에 필드를 추가하고 직렬화를 깜빡하면 테스트가 깨지게 만든다.

> **구현하며 알게 된 것 — 왕복 비교만으로는 부족하다.**
> `Macros.toDto()`가 `null`을 `0.0`으로 바꾸도록 일부러 망가뜨려 확인해보니, **왕복 비교 테스트는 그대로 통과했다.** 변형이 내보내기 양쪽에 똑같이 적용돼서 두 결과가 여전히 같기 때문이다.
>
> 그래서 안전장치를 세 겹으로 둔다:
> 1. **왕복 비교** — 값이 사라지거나 순서가 뒤집히는 것을 잡는다
> 2. **표적 검증** — `null` vs `0.0` 구분처럼 *양쪽이 똑같이 뭉개지는* 변형을 잡는다. 왕복 비교와 중복처럼 보이지만 지우면 안 된다
> 3. **필드 완전성 검사** — 엔티티 필드 목록을 리플렉션으로 대조해, 필드를 추가하고 DTO 반영을 깜빡하면 깨지게 한다

## 2. 무엇을 저장하는가

### 로컬 (기기 안)

| 위치 | 내용 | 동기화 대상 |
|---|---|---|
| Room DB (`leanbulk.db`) | 모든 기록 | ○ (JSON으로 변환해서) |
| DataStore | 동기화 메타데이터 | **×** |
| EncryptedSharedPreferences | 드롭박스 토큰, AI API 키 | **×** |
| 앱 내부 저장소 `backups/` | 직전 스냅샷 몇 개 | × |

**동기화 메타데이터를 DB에 넣으면 안 된다.** 동기화가 DB 내용을 통째로 갈아끼우므로, "마지막 동기화 rev"를 DB에 두면 갈아끼울 때 같이 날아가서 매번 처음부터가 된다.

DataStore에 두는 것:
- `lastSyncedRev` — 마지막으로 주고받은 드롭박스 파일 버전
- `lastSyncedAt` — 시각 (화면 표시용)
- `lastSyncedHash` — 그때 로컬 스냅샷의 해시. **로컬이 변했는지 판단하는 기준**
- `pendingConflict` — 충돌이 감지됐는지

### 원격 (드롭박스 앱 전용 폴더)

```
/leanbulk-snapshot.json.gz     ← 유일한 동기화 파일
```

앱 전용 폴더(App Folder) 권한만 쓴다. 사용자의 다른 드롭박스 파일엔 접근하지 않는다.

인증은 PKCE + 단기 토큰 + 리프레시 토큰. **리프레시 토큰은 EncryptedSharedPreferences**에 저장한다 (AI API 키와 같은 곳).

## 3. 언제 동기화하는가

실시간 동기화는 안 한다. 개인 앱에 과하고, 배터리·네트워크를 계속 쓴다.

### 앱이 앞으로 나올 때 — 받기

```
드롭박스 링크 안 돼 있음      → 아무것도 안 함
원격 파일 없음                → 첫 동기화. 올리기로 전환
remoteRev == lastSyncedRev    → 원격 그대로. 할 일 없음
remoteRev != lastSyncedRev
  └ 로컬이 안 변했으면        → 받아서 적용
  └ 로컬도 변했으면           → ★ 충돌. 사용자에게 물어봄
```

"로컬이 변했는지"는 **현재 스냅샷의 해시를 `lastSyncedHash`와 비교**해서 판단한다. 이 방식이면 쓰기 경로를 하나도 안 건드려도 된다 (dirty 플래그를 곳곳에 심을 필요 없음).

### 앱이 뒤로 갈 때 — 올리기

```
1. 대기 중인 자동저장을 즉시 확정 (로컬 쓰기, 빠름)
2. 스냅샷을 떠서 해시 비교 → 안 변했으면 여기서 끝
3. WorkManager에 업로드 작업 등록
4. 워커: WriteMode.update(lastSyncedRev)로 업로드
   ├ 성공  → lastSyncedRev / Hash / At 갱신
   └ 거부  → 그 사이 다른 기기가 올린 것. pendingConflict 표시
```

### 왜 WorkManager인가

`MainActivity.onPause()`의 `flushPendingSaves()`는 `viewModelScope.launch`라 **기다리지 않고 리턴한다.** 지금은 로컬 쓰기(ms)라 대체로 성공하지만, 여기에 네트워크 업로드(초 단위)를 얹으면 프로세스가 먼저 죽어서 업로드가 날아간다.

WorkManager는 프로세스가 죽어도 살아남고, 네트워크가 없으면 생길 때까지 기다렸다가 재시도한다. 역할을 이렇게 나눈다:

- **로컬 플러시** — 빠르고 즉시. `onStop`에서 그대로
- **네트워크 업로드** — 느리고 불확실. WorkManager

앱 수명주기 감지는 Activity의 `onPause`가 아니라 **`ProcessLifecycleOwner`** 로 한다. 화면 회전이나 탭 전환에 반응하지 않고, 앱 전체가 백그라운드로 갈 때만 동작한다.

## 4. 충돌 처리

### 자동 병합은 하지 않는다

두 기기가 각각 편집한 걸 자동으로 합치는 건 **레코드 단위 동기화**가 필요한데, 지금 구조로는 불가능하다 (아래 5장). 대신 **손실 없이 사용자에게 넘긴다.**

### 사전 감지 — 덮어쓰기 자체를 막는다

드롭박스는 파일 버전마다 `rev` 문자열을 준다. 업로드할 때 `WriteMode.update(lastSyncedRev)`를 쓰면, 그 사이 다른 기기가 올렸을 경우 **덮어쓰는 대신 거부**한다.

이게 핵심이다. "백업을 남긴다"는 사고가 난 뒤의 **복구** 장치지만, `rev` 검사는 **사고 자체를 막는다.** 드롭박스가 공짜로 주는 기능이라 안 쓸 이유가 없다.

### 충돌이 나면

양쪽을 요약해서 보여주고 사용자가 고른다. 자동으로 아무것도 결정하지 않는다.

```
동기화 충돌 — 두 기기에서 각각 기록이 바뀌었습니다

  이 기기    2026-09-02 14:30 수정 · 187일 기록 · 운동 412세션
  드롭박스   2026-09-02 16:05 수정 · 186일 기록 · 운동 408세션

  [ 이 기기 것 쓰기 ]  [ 드롭박스 것 쓰기 ]  [ 나중에 ]

  ※ 선택하지 않은 쪽은 백업으로 남습니다
```

- 고르지 않은 쪽은 `backups/`에 JSON으로 남긴다. **어느 쪽을 골라도 데이터가 사라지지 않는다**
- 충돌이 해결될 때까지 자동 업로드를 멈춘다. 안 그러면 계속 거부당하며 배터리만 쓴다
- 백업에서 필요한 부분만 골라 되살리는 건 **3번(JSON 가져오기)의 선택적 병합 기능**이 담당한다. 여기서 다시 만들지 않는다

### 적용 전엔 항상 백업

받은 걸 적용하기 직전에 현재 상태를 `backups/`에 남긴다. 최근 5개만 유지하고 오래된 건 지운다.

## 5. 왜 레코드 단위 병합을 안 하는가

이상적으로는 "폰에서 넣은 운동"과 "PC에서 넣은 식단"이 자동으로 합쳐지는 게 맞다. 지금 구조에서는 못 한다.

**`replaceDay()`가 행 ID를 계속 파괴한다.** 자동저장 700ms마다 그날 기록을 **전부 지우고 `id = 0`으로 재삽입**한다 (`MealDao.replaceDay`, `WorkoutDao.replaceDay`). 그래서:

- 행 ID가 편집할 때마다 바뀐다 → "같은 행"을 두 기기에서 대조할 방법이 없다
- `updatedAt` 컬럼을 붙여도 무의미하다 → 모든 행이 항상 "방금 새로 생김"이다

즉 **`updatedAt`을 지금 미리 넣어두는 건 이득이 없다.** 0단계에서 붙여두자는 안을 검토했다가 버렸다.

레코드 병합을 하려면 선행 조건이 있다:

1. 자동저장을 `delete + insert`에서 **안정 ID 기반 upsert**로 교체
2. 삭제를 실제 삭제가 아니라 **묘비(tombstone)** 로 — 안 그러면 "지운 것"과 "아직 안 받은 것"을 구분 못 함
3. 그 위에 행 단위 `updatedAt` + 병합 로직

1번만으로도 자동저장 경로를 통째로 다시 짜야 한다. **혼자 쓰는 기기 두 대를 번갈아 쓰는** 사용 방식에선 전체 스냅샷 + 충돌 감지로 충분하므로, 실제로 불편해지기 전까지 하지 않는다.

## 6. 받은 걸 적용하는 방법

JSON을 받아서 DB에 넣을 때 주의할 점.

**하나의 트랜잭션 안에서 전체 교체.** 중간에 실패하면 통째로 롤백돼야 한다. 반쯤 덮어쓴 상태가 제일 나쁘다.

**편집 중이던 draft를 반드시 처리해야 한다.** Room의 Flow는 변경을 알아서 알리지만, `MainViewModel`이 들고 있는 draft(`_workoutDraft`, `_dietDraft`)는 **DB와 무관한 메모리 상태라 자동으로 안 바뀐다.** 옛 draft가 남아 있으면 불러오기가 끝난 0.7초 뒤 자동저장이 돌면서 **방금 불러온 기록을 덮어쓴다.**

→ 순서를 이렇게 묶는다 (`MainViewModel.applyImport`):

1. **대기 중인 자동저장 작업을 취소**한다 (flush가 아니라 cancel — 옛 draft를 쓰면 안 되므로)
2. 현재 상태를 되돌림점으로 저장한다
3. 스냅샷으로 교체한다
4. `loadWorkoutDraft` / `loadDietDraft`로 draft를 **DB에서 다시 읽는다**

> **`Activity.recreate()`로는 해결되지 않는다.** 처음엔 그렇게 잡았다가 구현하며 알았는데, `recreate()`는 설정 변경과 같은 취급이라 **ViewModel이 그대로 살아남는다.** 화면만 다시 그려지고 draft는 옛날 것 그대로다.

**적용은 앱이 앞에 있을 때만.** 백그라운드에서 몰래 DB를 갈아끼우면 위의 draft 문제가 그대로 터진다. 받기는 항상 포그라운드 진입 시점에만 한다.

## 7. 만드는 순서

동기화 자체보다 **선행 작업이 대부분**이다.

- [x] **JSON 직렬화 + 왕복 테스트** — `data/backup/`(`Snapshot`, `SnapshotCodec`), `Repository.exportSnapshot()` / `importSnapshot()`, 계측 테스트 5개 통과
- [x] **백업/복원 UI** — 내보내기 탭의 "백업 · 복원" 섹션(`ExportScreen.BackupSection`), 확인 다이얼로그, 적용 전 되돌림점 자동 저장(`BackupFiles.saveRollbackPoint`)
- [ ] **0단계 — 파괴적 마이그레이션 제거** (`fallbackToDestructiveMigration()` 삭제 + 스키마 export)
  - WAL 끄기는 **불필요해졌으므로 하지 않는다**
- [ ] **JSON 선택적 병합** (로드맵 3번 나머지 — "남의 루틴 중 이것만 가져오기")

여기까지가 동기화 없이도 필요한 부분이고, 아래부터는 **후순위**다 — 카탈로그 계층·운동 목적 설정·AI 챗을 다 만든 뒤에 착수한다.

- [ ] **드롭박스 개발자 앱 등록** — 사용자가 콘솔에서 직접 해야 함
- [ ] **드롭박스 인증 + 업/다운로드**
- [ ] **동기화 상태 기계 + 충돌 UI**
- [ ] **CMP 데스크탑 앱** — Room이 데스크탑(JVM)을 지원하므로 `data/`는 재사용. 드롭박스 인증만 데스크탑용(브라우저 PKCE)으로 따로

**백업/복원 UI까지만 해도 실질적인 안전망이 생긴다.** 드롭박스가 늦어져도 수동 백업/복원이 가능해지고, 드롭박스 등록이 사용자 작업이라 막혀 있어도 진행할 수 있다.
